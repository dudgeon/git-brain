TL;DR — Recommended approach: “Repo = Brain” (Option A)

Each connected repo becomes its own brain with its own UUID, MCP URL, storage, and search scope. Because almost everything already keys on the brain UUID (brains/{uuid}/), this reuses all existing per-brain isolation and leaves the entire MCP tool layer untouched. It directly matches “access one brain, not the other,” and it works even when both repos live under the same GitHub account.

The problem (today)

A “brain” is currently 1:1 with a GitHub installation, and setup only ever syncs the first repo (repos[0]). So you can’t add a second repo as its own isolated brain — and a few write surfaces already misbehave for anyone who owns more than one installation:

  • Only one repo syncs. Granting the App access to more repos silently does nothing.
  • Arbitrary brain selection. Web clips, the bookmarklet page, and the OAuth success page all do LIMIT 1 — non-deterministic which brain you get.
  • Wrong-brain routing risk. Push and uninstall webhooks resolve by installation only, not by repo.

How Option A works

GitHub installone per account/org
→
3 repos grantedrepo-a · repo-b · repo-c
→
Brain A/mcp/uuid-a · brains/uuid-a/
Brain B/mcp/uuid-b · brains/uuid-b/
Brain C/mcp/uuid-c · brains/uuid-c/

Each brain is fully isolated: separate R2 prefix, separate AI Search filter, separate email sub-address, separate clip target. You connect each as its own connector and use whichever you want.

What actually changes

The big win of Option A: the tool layer and isolation primitives are already per-brain. The work concentrates in onboarding, webhooks, and the three LIMIT 1 surfaces.
